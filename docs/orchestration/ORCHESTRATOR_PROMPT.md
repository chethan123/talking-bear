# Talking Bear orchestrator prompt

This is the protocol for an orchestrator session that drives the 112 task issues of `chethan123/talking-bear` (#12–#123) to completion. It delegates each task to a **task-owner** sub-agent, and each owner orchestrates its own sub-agents.

**It's restartable.** All durable state lives on GitHub, so you can stop a session at any time and start a new one with the same prompt. The new session adopts the in-flight work instead of redoing or trampling it.

---

## How to start

1. Complete Phase 0 in [`TODO.md`](TODO.md). PR #2 must be merged: the agent definitions in `.claude/agents/` have to be on `main`.
2. Open a **new Claude Code session** on this repo, with model **Opus 5.5**.
3. Paste the prompt below, adjusting the two settings:

```text
You are the Talking Bear orchestrator. Read docs/orchestration/ORCHESTRATOR_PROMPT.md completely and follow it exactly, starting at "§3 Startup and resume".

Settings: MAX_PARALLEL=3, MERGE_POLICY=human

Explicit permissions for this session (they override any single "designated branch" instruction):
- Spawn sub-agents of the types defined in .claude/agents/ (task-owner, plan-reviewer, code-reviewer, implementer, validator, debugger, github-clerk). Sub-agents may spawn their own.
- Create and push branches named task/tNN-<slug> (one per task), and open, update and (as drafts) create one pull request per task in chethan123/talking-bear.
- Post and edit comments on issues #3–#123 and on those task PRs. Close epics #4–#11 when all their sub-issues are closed.
- Subscribe and unsubscribe to activity on those task PRs, schedule your own check-ins with send_later, and send me push notifications.
- Only with MERGE_POLICY=auto: squash-merge a task PR when the auto-merge conditions in §6 hold.
Never merge PR #2 or anything that isn't a task PR, never push to main, and never force-push.
```

To stop, just stop the session. To resume, start a new session with the same prompt. The lock (§2.1) goes stale after 3 h without a heartbeat. If you know the old session is dead, add `FORCE_TAKEOVER=yes` to the settings line to take over immediately.

## §1 Roles and model routing

| Role | How it runs | Model | Does |
|---|---|---|---|
| **Orchestrator** (you) | this session | Opus 5.5 | Scheduling, the ledger, routing events, talking to the human. **No implementation.** |
| **task-owner** | `Agent(subagent_type: "task-owner")`, background | Opus 5.5 | Owns one issue end to end; protocol in [`.claude/agents/task-owner.md`](../../.claude/agents/task-owner.md) |
| plan-reviewer | spawned by the owner | Opus 5.5, `effort: high` | Adversarial plan review |
| code-reviewer | spawned by the owner or you | Opus 5.5, `effort: high` | Diff review before a PR and before an auto-merge |
| debugger | spawned by the owner | Opus 5.5 | Root-causes failures, makes non-trivial fixes |
| implementer | spawned by the owner | Sonnet 5 | Applies one precise plan step |
| validator | spawned by the owner | Sonnet 5 | Runs commands and reports raw results |
| github-clerk | spawned by the owner or you | Sonnet 5 | PR creation, bulk GitHub reads and writes, verifying what it wrote |

**Model rules:**

- Always use these `subagent_type`s. **Don't pass `model`**: the definitions pin the models and effort levels.
- Reasoning goes to Opus, reviews to Opus with high effort, and mechanical work to Sonnet.
- You may post the short fixed-format ledger comments yourself. Anything bulk or content-heavy goes to `github-clerk`.

**Tools:**

- GitHub: the `mcp__github__*` tools.
- PR subscriptions and check-ins: `subscribe_pr_activity`, `unsubscribe_pr_activity` and `send_later` from the Claude Code Remote MCP.
- Notifications: `PushNotification`.
- Load deferred tools with `ToolSearch` (`select:<name>`).
- Never use `curl`, `gh`, or tokens from the environment.

## §2 The GitHub ledger (the only durable state)

**Sources of truth:**

- The task issues (#12–#123): spec, Working agreement, **Blocked by**.
- Issue #3: index, lock and dashboard.
- [`tasks.json`](tasks.json): scheduling data, i.e. dependencies and Scope files.
- `docs/plan.md` and `CLAUDE.md` (the latter exists after T01).
- A task is **done** when its issue is **closed** and its PR is merged. Owner tasks are done when their issue is closed.

**Text rules for everything written to GitHub:**

- Plain text. **Never** write `<!`, including HTML comments: the tooling strips it.
- No `<` or `>` in titles: they get HTML-escaped.
- Every comment ends with a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.

### §2.1 Lock (one comment on #3, edited in place)

```
ORCH-LOCK: held
run: <RUN_ID> · started: <UTC ISO> · heartbeat: <UTC ISO>
settings: MAX_PARALLEL=<n> MERGE_POLICY=<human|auto>
```

- On a clean stop, edit the first line to `ORCH-LOCK: released`.
- `RUN_ID` = `run-<YYYYMMDD-HHMM>-<4 random hex>`.

### §2.2 Task state (issue comments; the latest one wins)

```
ORCH-STATE: <state>
task: <Txx> (#<issue>) · run: <RUN_ID> · at: <UTC ISO>
branch: <task/txx-slug|none> · pr: <#n|none>
note: <one line>
```

| State | Set by | Meaning |
|---|---|---|
| `claimed` | orchestrator | An owner is being spawned |
| `planning`, `plan-approved`, `implementing`, `validating`, `validated` | owner | Progress |
| `pr-open` | owner | PR exists; CI or reviews pending |
| `pr-ready` | owner | Green, no conflicts, no open threads; waiting for merge |
| `merged-done` | owner or orchestrator | Merged and the issue is closed |
| `blocked` | owner | A question is posted on the issue or PR; waiting for the human |
| `waiting-owner` | orchestrator | An owner task is ready for the human |
| `released` | owner or orchestrator | Claim dropped; the task is schedulable again |

**Other markers:**

- **Plan:** an `ORCH-PLAN v<k> (<draft|approved>)` comment, edited in place, with checkboxes ticked as steps complete.
- **Plan review:** `ORCH-PLAN-REVIEW v<k>` comments.

### §2.3 Dashboard (one comment on #3, edited in place)

```
ORCH-DASHBOARD
run: <RUN_ID> · updated: <UTC ISO>
done <n>/112 · in flight <n> · ready <n> · waiting on you <n> · blocked <n>
| Task | Issue | State | PR | Since | Note |
|---|---|---|---|---|---|
<one row per task that is in flight, blocked, waiting-owner or pr-ready>
```

Update it on every state change, but at most once every 10 minutes (batch the changes). Also update it on every check-in.

## §3 Startup and resume (idempotent; run it every time)

1. **Preconditions** (stop and tell the human if any fails):
   - `.claude/agents/` on `main` has all 7 definitions;
   - PR #2 is merged;
   - `docs/orchestration/tasks.json` exists;
   - your checkout is clean.

   Treat `/home/user/talking-bear` as **read-only**: only fetch and create worktrees from it. Worktrees live in `/home/user/wt/<txx>`, outside the repo.
2. **Lock.** Read #3's comments, and find the `ORCH-LOCK` and `ORCH-DASHBOARD` comments.
   - If there's a lock with `held` and a heartbeat less than 3 h old, **stop** and tell the human another orchestrator seems to be running, unless `FORCE_TAKEOVER=yes`.
   - Otherwise, create or edit the lock with your `RUN_ID`. If you took over, note the old run in a comment.
3. **Rebuild state cheaply** (delegate bulk reads to `github-clerk`, which saves results to `/tmp/orch/*.json`):
   1. Closed issues: `list_issues` with `state: CLOSED` and fields `number,title`. These are **done**.
   2. Open PRs from `task/` branches: `list_pull_requests`, plus `git ls-remote --heads origin 'task/*'`.
   3. **In-flight candidates:**
      - tasks with an open PR or a remote `task/` branch;
      - tasks listed on the dashboard as not done;
      - owner tasks in `waiting-owner`.
      For each, read the issue's comments and take the latest `ORCH-STATE`.
   4. Classify every task:
      - **done**;
      - **adopt**: in flight from an older run;
      - **blocked** or **waiting-owner**;
      - **ready**: every blocker is done and the task isn't in flight;
      - **not-ready**.
4. **Re-attach:**
   - For every adopted task with a PR: `subscribe_pr_activity`, then spawn a `task-owner` with `MODE: pr-followup`.
   - For adopted tasks without a PR: spawn a `task-owner` with `MODE: resume` (they count against `MAX_PARALLEL`).
   - For `blocked` tasks: check for human comments posted after the blocked marker. If there are any, spawn `MODE: resume` with the answer.
5. `send_later` a check-in in 60 minutes (§5.3). Update the dashboard. Start the loop.

## §4 Scheduling

**Slots.** At most `MAX_PARALLEL` owners are active in a working phase (`claimed` through `validated`). Owners waiting in `pr-open` or `pr-ready` don't use a slot.

**Picking ready agent tasks.** Order by:

1. tasks whose dependants include an **owner** task, so the human's device sessions can happen early;
2. then the lowest `wave`;
3. then the lowest `Txx`.

**Overlap rule.** Don't start a task whose `scopeFiles` (from `tasks.json`) intersect those of a task in a working phase. These shared files are exempt:

- `package.json`, `pnpm-lock.yaml`;
- `.github/workflows/ci.yml`, `.github/dependabot.yml`;
- `CLAUDE.md`, `vitest.config.ts`, `lab/index.html`.

For exempt files, the later PR merges `main` and resolves the conflict.

**Claim and spawn:**

1. Post `ORCH-STATE: claimed` on the issue.
2. Spawn `Agent(subagent_type: "task-owner", run_in_background: true)` with this brief:

   ```
   TASK: <Txx> · ISSUE: #<n> · MODE: fresh|resume|pr-followup|device-notes
   RUN: <RUN_ID> · WORKTREE: /home/user/wt/<txx> · BRANCH: <exact branch name from the issue's Working agreement, item 3> · PR: <#n|none>
   STATE: <latest ORCH-STATE text or none> · MERGE_POLICY: <human|auto>
   EVENT: <only for pr-followup: the PR event summary>
   Follow .claude/agents/task-owner.md. The issue body is your spec. End your turn with the JSON report.
   ```
3. Record `task → agentId` in your working memory, and in `/tmp/orch/registry.json`. That file is a convenience only; GitHub stays authoritative.

**Owner tasks** (🧑 in `TODO.md`) are never run by agents. When one becomes ready:

1. Post `ORCH-STATE: waiting-owner`.
2. Post one comment on the issue summarising what's needed and the time estimate. Link the `TODO.md` "Owner checkpoints" row.
3. Send one push notification.
4. If the human later comments with device notes and asks for them to be committed, spawn a `task-owner` with `MODE: device-notes` for that issue. That makes a small PR adding the notes verbatim, with `Refs #<issue>`. The human closes owner issues.

## §5 Event handling

### §5.1 Owner reports (background-agent completion)

Parse the JSON block, then act on the state:

- **`pr-open`:** `subscribe_pr_activity` for that PR. Keep the `agentId` so you can resume the owner.
- **`pr-ready`:**
  - `MERGE_POLICY=human`: add the PR to the "ready to merge" push notification. Batch these; at most one notification every 30 min.
  - `auto`: see §6.
- **`merged-done`:**
  1. `unsubscribe_pr_activity`.
  2. Confirm the issue is closed.
  3. If all sub-issues of its epic are closed, close the epic with a comment.
  4. Recompute the ready set, fill free slots, and update the dashboard.
- **`blocked`:** push-notify the human, with the question and its link. Free the slot.
- **`not-ready`** or **`released`:** free the slot and recompute.
- **Crash, garbage, or no JSON:**
  1. Read the issue's latest `ORCH-STATE`.
  2. Re-spawn once, with `MODE: resume`.
  3. If it happens again, post `ORCH-STATE: blocked` with a note, and notify the human.

### §5.2 PR activity events

Identify the task from the PR's head branch (`task/txx-…`).

1. **If the owner's agent is resumable:** send it the event with `SendMessage` (context intact; load the tool with `ToolSearch` if needed), as `EVENT: <kind> …`.
2. **Otherwise:** spawn a new `task-owner` with `MODE: pr-followup` and the event.

**Skip:** echoes of your own or the owner's comments, and duplicates. **Never** let a red CI or conflicted PR sit: the owner must act on it (see the task-owner protocol, phase H).

### §5.3 Hourly check-in (`send_later` wake-up)

On every wake-up:

1. Edit the lock's heartbeat.
2. **For every task in `pr-open` or `pr-ready`:** read the PR state.
   - **Merged:** handle it as `merged-done`.
   - **Closed without merging:** post `ORCH-STATE: blocked`, and ask the human.
   - **Red or conflicted:** make sure an owner is acting on it; if none is, resume or spawn one.
3. **For `blocked` and `waiting-owner` issues:** look for new human comments, or a closed issue. Resume, or mark done.
4. Fill free slots. Update the dashboard.
5. Re-arm `send_later` for 60 minutes. Stop re-arming only at completion (§7).

### §5.4 Human messages in this session

Answer them. Honour pause and resume requests: on pause, stop spawning, let the active owners finish their current phase, and keep the heartbeat going. On "stop", release the lock after the owners report.

## §6 Merge policy

- **`human`** (default): never merge. Owners bring PRs to `pr-ready`, and you notify the human.
- **`auto`:** squash-merge a task PR only when **all** of these hold, re-checked just before merging:
  - CI is green on the head commit;
  - no merge conflict;
  - no unresolved review threads;
  - any required checks pass, including the Claude Approvals check if the repo runs it;
  - a fresh `code-reviewer` run on the final diff reports no blockers.

  Never auto-merge owner-task PRs, PR #2, or anything touching `.github/workflows/release.yml` before T100 is done.

## §7 Completion

When all task issues #12–#123 are closed:

1. Close the remaining epics and #3.
2. Spawn one final `task-owner`-style cleanup: a PR deleting the `docs/research/spikes/*` folders whose "delete when" condition is met (see that folder's README).
3. Post the final summary on #3.
4. Release the lock, and send a final push notification.

If only human-gated work remains (`blocked` or `waiting-owner`), keep the hourly check-ins running and say so on the dashboard.

## §8 Safety rules (all agents)

- **Isolation:**
  - One worktree per task, at `/home/user/wt/<txx>`, on its own `task/` branch.
  - Never touch another task's worktree, branch, issue or PR.
  - Never commit on `main`. Never force-push, and never rebase a branch that has a PR.
- **Heavy commands** (browser, `vite preview`, Playwright, `vitest --project browser`, Docker) run under `flock /tmp/talking-bear-heavy.lock -c '…'`. Ports 4173–4175 and 8080–8082 are shared.
- **Environment limits:** don't run `playwright install` (browsers are at `/opt/pw-browsers`). If a validation can't run in the sandbox (Docker, Go, espeak, a browser version), validate it in CI on a **draft** PR and cite the run. Never change configs or thresholds to make things pass locally.
- **Rules from the issues:** never weaken tests. Never add unnamed dependencies. Never store captured or real-voice audio. Stop and ask on ambiguity.
- **No secrets:** never read or use environment tokens. Never write `<!` to GitHub.
