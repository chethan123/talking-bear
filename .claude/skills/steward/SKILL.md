# Steward rules for Talking Bear task PRs

These rules apply to every pull request from a `task/txx-*` branch. They add to your session's own PR rules and never relax them.

## Who acts (one actor per PR)

- **Orchestrator running:** if issue #3 has a comment starting `ORCH-LOCK: held` with a heartbeat less than 3 h old, the orchestrator (`.claude/skills/orchestrate/SKILL.md`) and its task owners own every task PR.
  - If you *are* that orchestrator or one of its task owners, follow your own protocol. These rules still apply.
  - Otherwise, **don't act on task PRs**. Tell the human the orchestrator owns them.
- **No live orchestrator, or the human explicitly asks you:** you may drive the PR. Record `run: steward` and `owner: steward` in any `ORCH-STATE` you post.

## Identify the task

- The branch `task/t07-…` means task **T07**. The issue number is in the PR body (`Closes #n`), or in `.claude/skills/orchestrate/tasks.json` (`id` → `issue`).
- The issue body is the spec, and `docs/plan.md` is the source of truth. The approved plan is the `ORCH-PLAN … (approved)` comment on the issue.

## Before pushing anything

1. Work in the task's own worktree, `/home/user/wt/<txx>`. Create it from `origin/<branch>` if it's missing. Never work in `/home/user/talking-bear` itself, and never in another task's worktree.
2. Run the issue's **Validation** commands that the change affects, plus `pnpm verify` (lint, format, typecheck and unit tests).
3. Wrap browser, `vite preview`, Playwright, `vitest --project browser` and Docker commands in `flock /tmp/talking-bear-heavy.lock -c '…'`. Other tasks share the machine and ports 4173–4175 and 8080–8082.
4. **Can't run it here?** If a validation can't run in the sandbox (Docker, Go, espeak-ng, the pinned Playwright browser), rely on this PR's CI run and cite it. Don't run `playwright install`, and don't edit configs to make it pass locally.

## CI red

- Root-cause it. "Flaky" is not a root cause.
- Never skip, disable, quarantine or loosen a test, lint rule, coverage threshold, size budget or `check-dist` rule.
- If the failure is also red on `main`, it isn't this PR's. Comment once on the PR, naming the check and why, and link any fix PR.

## Merge conflicts

- Merge `origin/main` into the branch; never rebase or force-push a branch with a PR.
- Regenerate `pnpm-lock.yaml` with `pnpm install`, never by hand.
- Regenerate generated files with their scripts:
  - `pnpm fixtures`;
  - `node scripts/gen-bear-parts.ts`;
  - `pnpm silero:extract`;
  - `pnpm corpus --write-hashes`.

## Review comments

- Small, local asks (nits, renames, an added test, a one-function refactor): implement, push, and reply on the thread saying what changed.
- Anything that changes the task's Scope, an interface other tasks use, or the plan: reply with a proposal and ask the human. Don't push it.

## Scope

- Change only the issue's **Scope** files, plus `pnpm-lock.yaml`.
- Never add a dependency the issue doesn't name.
- Never store or commit captured or real-voice audio (plan Q2).

## Ledger

After each round, post a status comment on the **issue** (not the PR), using exactly this format:

```
ORCH-STATE: <pr-open|pr-ready|merged-done|blocked>
task: <Txx> (#<issue>) · run: <steward, or your orchestrator run id> · owner: <steward, or your OWNER_ID> · at: <UTC ISO>
branch: <branch> · pr: #<n>
note: <one line>
```

- **`pr-ready`** means: CI green on the head commit, no conflicts, no unresolved review threads. **Never merge**: the human merges, or the orchestrator does under `MERGE_POLICY=auto`.
- **After a merge:**
  1. confirm the issue closed; if not, close it with a comment linking the PR;
  2. post `merged-done`;
  3. unsubscribe from the PR;
  4. remove the worktree.

## Text rules for GitHub

- Never write `<!`, including HTML comments; the tooling strips it.
- Avoid `<` and `>` in titles.
- Every comment and reply ends with a blank line, then `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.
- Use only the GitHub MCP tools. Never use tokens from the environment.
