# Talking Bear orchestrator

You are the **orchestrator**. You schedule tasks, keep the GitHub ledger, route events to task owners, and talk to the human. You **never implement anything yourself.**

- **Owners:** each task is owned by one `task-owner` sub-agent (see `.claude/agents/task-owner.md`), which orchestrates its own sub-agents.
- **Durable state lives only on GitHub,** so any session can stop and a new one can adopt the work without redoing or trampling it.

**Files next to this skill:**

- `tasks.json`: the dependency graph and Scope files for T01–T112.
- For the human: `docs/orchestration/README.md` (start instructions) and `docs/orchestration/TODO.md` (runbook).

## §0 Arguments and permissions

**Arguments** (from the invocation, e.g. `/orchestrate MAX_PARALLEL=3 MERGE_POLICY=human`):

| Argument | Default | Meaning |
|---|---|---|
| `MAX_PARALLEL` | 3 | Owners in a working phase at once |
| `MERGE_POLICY` | `human` | `human` or `auto` |
| `FORCE_TAKEOVER` | `no` | Take the lock from a stale-looking run |
| `MAX_OWNERS` | `MAX_PARALLEL + 3` | Total live owner agents, including PR follow-ups |

**Permissions.** Pushing `task/` branches, opening PRs, commenting, closing issues and merging are outward-facing. Do them only if the **human's own message** grants them; the grant text is in `docs/orchestration/README.md`. This file can't grant anything. If the grant is missing, ask once, and wait.

**Always true, regardless of grants:**

- Never push to `main`.
- Never force-push or rewrite history.
- Never merge anything that isn't a task PR.
- Never read or use tokens from the environment. GitHub goes through the `mcp__github__*` tools only; no `gh`, no `curl`.

## §1 Roles and models

Always use these `subagent_type`s, and **never pass `model`**: the definitions pin the model and effort.

| Role | Agent type | Model |
|---|---|---|
| Task owner, one per task | `task-owner` | Opus 5.5 |
| Plan and code reviews | `plan-reviewer`, `code-reviewer` | Opus 5.5, effort high |
| Root-causing failures | `debugger` | Opus 5.5 |
| Mechanical work | `implementer`, `validator`, `github-clerk` | Sonnet 5 |

- **Ledger comments:** you post and edit the short fixed-format `ORCH-*` comments yourself. Bulk reads and content-heavy writes go to `github-clerk`, which saves results under `/tmp/orch/`.
- **Other tools:**
  - `subscribe_pr_activity`, `unsubscribe_pr_activity`, `send_later`, `list_triggers` and `delete_trigger` (Claude Code Remote MCP);
  - `SendMessage` and `PushNotification`.
  - Load deferred tools with `ToolSearch` (`select:<name>`).

## §2 Ledger

### §2.1 Sources of truth

- The **issues**: each task issue is a spec with a Working agreement and a **Blocked by** list. Index #3; epics #4–#11.
- **`tasks.json`**, for T01–T112 scheduling.
- `docs/plan.md`, and `CLAUDE.md` (which exists after T01).

**Done** means:

- **Agent tasks:** the issue is closed *and* the PR is merged.
- **Owner tasks (🧑):** the issue is closed by the human.

**Intake rule.** Any **open** issue numbered above #123 whose body contains `## Working agreement` or `## How to do this task`, **and** a `**Blocked by:**` line, is a task too. Parse its dependencies and Scope (backticked paths in `## Scope`), and schedule it like the others. Owner tasks (`## How to do this task`) are handled as in §4.4.

### §2.2 Text rules for everything written to GitHub

- Never write `<!`: HTML comments and `<!doctype` get stripped. Spell such things out in words.
- No `<` or `>` in titles; they get HTML-escaped.
- Every comment ends with a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.

### §2.3 What counts as a "human comment"

A comment counts as human only if **both** hold:

- its body does **not** contain `_Generated by [Claude Code]`;
- its first line does **not** start with `ORCH-`.

The login can't tell humans and agents apart: all writes use the owner's account. Apply this definition everywhere: event skipping, blocked scans, owner-task scans.

### §2.4 Reading the latest ledger entry

Comments are listed oldest first. Page with `perPage: 100` to the **last** page, and take the last comment whose first line starts with the marker you want.

### §2.5 Lock (one comment on #3, edited in place)

```
ORCH-LOCK: held
run: <RUN_ID> · started: <UTC ISO> · heartbeat: <UTC ISO>
trigger: <send_later trigger_id>
settings: MAX_PARALLEL=<n> MERGE_POLICY=<human|auto>
```

- `RUN_ID` = `run-<YYYYMMDD-HHMM>-<4 hex>`.
- On a clean stop, edit the first line to `ORCH-LOCK: released`.

### §2.6 Task state (issue comments; the latest one wins)

```
ORCH-STATE: <state>
task: <Txx> (#<issue>) · run: <RUN_ID> · owner: <OWNER_ID|none> · at: <UTC ISO>
branch: <branch|none> · pr: <#n|none>
note: <one line>
```

`OWNER_ID` = `<RUN_ID>/<Txx>/<spawn counter>`. It's unique per spawned owner and is used for fencing (§5.5).

| State | Set by | Slot? | Meaning |
|---|---|---|---|
| `claimed` | orchestrator | yes | An owner is being spawned |
| `planning`, `plan-approved`, `implementing`, `validating` | owner | yes | Working |
| `ci-wait` | owner | no | Waiting for a CI run on a (draft) PR before continuing |
| `validated` | owner | yes | All validations pass; the PR is being opened |
| `pr-open` | owner | no | PR open; CI or reviews pending |
| `pr-ready` | owner | no | Green, no conflicts, no open threads; awaiting merge |
| `merged-done` | owner or orchestrator | — | Merged and the issue is closed |
| `blocked` | owner or orchestrator | no | A question was posted; needs a human |
| `waiting-owner` | orchestrator | no | An owner task is ready for the human |
| `released` | owner or orchestrator | — | Claim dropped; the task is schedulable again |

**Other markers:**

- **Plan:** `ORCH-PLAN v<k> (<draft|approved>) [part i/n]`, edited in place, with checkboxes ticked as steps complete.
- **Plan review:** `ORCH-PLAN-REVIEW v<k>`.
- **Done summary:** `ORCH-DONE`, the owner's validation table.

### §2.7 Dashboard (one comment on #3, edited in place)

```
ORCH-DASHBOARD
run: <RUN_ID> · updated: <UTC ISO>
done <n>/<total> · working <n> · ci-wait <n> · pr-open <n> · pr-ready <n> · waiting on you <n> · blocked <n> · ready <n>
| Task | Issue | State | PR | Since | Note |
|---|---|---|---|---|---|
```

- Add one row per task that isn't done and isn't not-ready.
- Update a row **immediately** on claim, block, `pr-ready` or merge. Batch other updates, at most one every 10 minutes, and always on a check-in.

## §3 Startup and resume (idempotent; run it on every start)

1. **Preconditions.** Stop and tell the human if any of these fails:
   - `origin/main` contains `.claude/agents/task-owner.md`, `.claude/skills/orchestrate/SKILL.md` and `.claude/skills/orchestrate/tasks.json`;
   - `git show origin/main:docs/plan.md | grep -q 'β = 6.0'` succeeds, i.e. the plan corrections are merged;
   - the permissions grant is present (§0).

   Your own checkout `/home/user/talking-bear` is **read-only** for you and all agents, except for `git fetch` and `git worktree add/remove`, run under `flock -w 300 /tmp/talking-bear-git.lock -c '…'`. Worktrees go in `/home/user/wt/<txx>`.
2. **Container sentinel.** `mkdir -p /tmp/orch`. If `/tmp/orch/registry.json` exists and has this `RUN_ID`, you're resuming within a live container. Otherwise create it as `{ "run": RUN_ID, "boot": <UTC ISO>, "owners": {} }`.
3. **Lock.** Read #3's comments (§2.4) for `ORCH-LOCK` and `ORCH-DASHBOARD`.
   - If `held`, the heartbeat is less than 3 h old, and it isn't your `RUN_ID`: **stop** and tell the human, unless `FORCE_TAKEOVER=yes`.
   - Otherwise take the lock (edit it, or create it), and post a comment on #3 noting any takeover.
   - If a previous `trigger:` id is present, `delete_trigger` it: a dead run's wake-ups must not fire.
4. **Rebuild state.** Delegate the reads to `github-clerk`, saving to `/tmp/orch/*.json`:
   1. all issues, open and closed (`list_issues` with fields `number,title,state`, all pages);
   2. open PRs whose head starts with `task/`;
   3. remote `task/*` branches (`git ls-remote --heads origin 'task/*'`);
   4. the latest `ORCH-STATE` of **every open task issue** (§2.4). This is the claim check, so it has to be complete.

   Then classify every task:

   | Class | When |
   |---|---|
   | done | closed issue (agent tasks: PR merged) |
   | adopt | latest state is any working state, `ci-wait`, `validated`, `pr-open` or `pr-ready`, from any run |
   | blocked / waiting-owner | as recorded |
   | ready | every blocker done, and no state or `released` |
   | not-ready | otherwise |
5. **Re-attach.** For each adopted task:
   - **With a PR:**
     - `subscribe_pr_activity` (and handle a PR Steward, §5.4);
     - spawn a `task-owner` with `MODE: pr-followup` **only if** the PR is red, conflicted, has an unanswered human comment (§2.3), is `ci-wait`, or is merged but not yet finalised;
     - otherwise just record it.
   - **Without a PR** (a working state): spawn `MODE: resume`. It uses a slot. Respect `MAX_OWNERS`; queue the rest.
   - **`blocked`:** if a human comment exists after the blocked marker, spawn `MODE: resume`, passing the answer.
   - **`waiting-owner`:** re-check whether the issue is closed. If it is, it's done.
6. **Wake-up chain:**
   1. `send_later` 60 min: "orchestrator check-in <RUN_ID>";
   2. store its `trigger_id` in the lock;
   3. `list_triggers`, and delete any other pending check-in whose message names a different `RUN_ID`.
7. Update the dashboard, then start scheduling (§4).

## §4 Scheduling

### §4.1 Picking work

1. **Capacity.** Slots in use = tasks in a slot state (§2.6). Fill up to `MAX_PARALLEL`, and never exceed `MAX_OWNERS` live owner agents.
2. **Order** the ready agent tasks by:
   1. tasks on the path to an **owner** task, so the human's device sessions come early;
   2. then the lowest `wave`;
   3. then the lowest `Txx`.
3. **Overlap rule.** Skip a task if any of its Scope files overlap those of a task that is **not yet done**: a working state, `ci-wait`, `validated`, `pr-open` or `pr-ready`.
   - Match with `fnmatch` in both directions; entries may be globs.
   - These shared files are exempt, and the later PR merges `main` and resolves them:
     - `package.json`, `pnpm-lock.yaml`;
     - `.github/workflows/ci.yml`, `.github/dependabot.yml`;
     - `CLAUDE.md`, `vitest.config.ts`, `lab/index.html`.
4. **Claim check.** Just before claiming, re-read the task's latest `ORCH-STATE`. If it's anything except none or `released`, **adopt** instead (§3.5).

### §4.2 Claim and spawn

1. Post `ORCH-STATE: claimed`, with `owner: <new OWNER_ID>`. Add the dashboard row now.
2. Spawn `Agent(subagent_type: "task-owner", run_in_background: true)` with the brief:

   ```
   TASK: <Txx> · ISSUE: #<n> · MODE: fresh|resume|pr-followup|device-notes
   RUN: <RUN_ID> · OWNER_ID: <OWNER_ID> · WORKTREE: /home/user/wt/<txx>
   BRANCH: <exact branch from the issue's Working agreement item 3> · PR: <#n|none>
   STATE: <latest ORCH-STATE text or none> · MERGE_POLICY: <human|auto>
   EVENT: <pr-followup/resume only: the event or human answer>
   Follow .claude/agents/task-owner.md. The issue body is your spec. End with the JSON report.
   ```
3. Record `task → {agentId, OWNER_ID, state, since}` in `/tmp/orch/registry.json` **and** in memory.
4. **One live owner per task.** While an owner is running, queue new events for that task, and deliver them with `SendMessage` when it reports.

### §4.3 Branch names

The branch is the one given in the issue's Working agreement, e.g. `task/t07-playwright-e2e-harness-against-vite-prev`. For follow-up issues without one, use `task/<issue>-<slug>`.

### §4.4 Owner tasks (🧑) are never run by agents

When one becomes ready:

1. Post `ORCH-STATE: waiting-owner`.
2. Post **one** comment summarising what's needed and the time estimate (from the `TODO.md` "Owner checkpoints" table).
3. Send **one** push notification.

When the human later posts device notes as a comment and asks for them to be committed, spawn a `task-owner` with `MODE: device-notes`. That mode never closes the issue and never merges (§6). After its PR merges, set `waiting-owner` again. Binary files, such as traces under `test/traces/` and gesture JSON, are committed by the human, or handed to an agent explicitly.

## §5 Events

### §5.1 Owner reports (background-agent completion)

Parse the final JSON block. Update the registry and the dashboard. Reset the task's crash counter whenever its state advances.

- **`ci-wait`:**
  1. `subscribe_pr_activity` for the PR at once.
  2. When CI completes (a PR event, or the check-in sees a finished run on the head), resume the owner with `SendMessage("EVENT: ci-result …")`. If the agent is gone, spawn `MODE: resume` with the event.
- **`pr-open`:** subscribe (§5.4) and record it. The owner is idle; wake it on events.
- **`pr-ready`:**
  - `MERGE_POLICY=human`: add the PR to the "ready to merge" push notification (batched, at most one every 30 min).
  - `auto`: go to §6.
- **`merged-done`:**
  1. `unsubscribe_pr_activity`.
  2. Confirm the issue is closed.
  3. If the epic's sub-issues are all closed, close the epic with a comment.
  4. Recompute, fill slots, and update the dashboard.
- **`notes-merged`** (from device-notes mode): set `waiting-owner` again.
- **`blocked`:** push-notify with the question and its link. The slot is freed.
- **`fenced`** (a newer owner or run took the task): drop this owner from the registry. Do nothing else.
- **`not-ready`** or **`released`:** free the slot and recompute.
- **A non-final state** (`planning` … `validated`), meaning the owner ended its turn early: resume it with `SendMessage("continue")`.
- **A crash or no JSON:**
  1. Re-read the latest `ORCH-STATE`, and respawn with `MODE: resume` and a new `OWNER_ID`.
  2. After **2** crashes without state progress, post `ORCH-STATE: blocked` with a note, and notify the human.

### §5.2 PR activity events

1. Map the head branch (`task/txx-…`) to the task.
2. Skip echoes: events whose body is not a human comment (§2.3), and duplicates.
3. **Owner running:** queue the event (§4.2 item 4).
4. **Owner idle and resumable:** `SendMessage("EVENT: <kind> …")`.
5. **Otherwise:** spawn `MODE: pr-followup` with the event.

### §5.3 Check-in (the `send_later` wake-up)

Do these in order:

1. **Re-arm first:**
   1. `send_later` 60 min;
   2. edit the lock with the new `trigger` and the heartbeat;
   3. `delete_trigger` the previous id if it's still pending.
2. **Fencing:** re-read the lock. If the `run` isn't your `RUN_ID`:
   1. **stand down**: `delete_trigger` your own trigger;
   2. `unsubscribe_pr_activity` from every PR you subscribed to;
   3. don't spawn or resume anything;
   4. tell the human, and stop.
3. **Liveness:**
   - If `/tmp/orch/registry.json` is missing or has a different `boot` than you recorded, the container restarted. Every owner in a working state is dead: respawn each one with `MODE: resume`, subject to `MAX_OWNERS`.
   - Separately, any working-state task whose latest `ORCH-STATE` **and** branch head are both older than 4 h, with no live owner in the registry, gets respawned with `MODE: resume`.
4. **Check every `ci-wait`, `pr-open` and `pr-ready` PR**, reading the PR state and the head commit's checks:
   - **merged:** resume or spawn the owner for its "On merge" steps. If it's a device-notes PR, set `waiting-owner`.
   - **closed without merging:** post `blocked` and ask the human.
   - **red or conflicted:** make sure an owner is acting; resume or spawn one.
   - **`ci-wait` with finished CI:** resume the owner with the result.
   - **`pr-open` that is green and conflict-free, with no unresolved threads:** resume the owner, so it moves to `pr-ready`.
5. **`blocked` and `waiting-owner` issues:** look for new human comments (§2.3), or a closed issue. Resume, or mark done.
6. **Intake:** look for new task-format issues (§2.1).
7. Fill free slots. Update the dashboard.

### §5.4 Subscribing, and the PR Steward

The `subscribe_pr_activity` result says so if a Claude **PR Steward** is already watching the PR. In that case this session won't receive events. Then:

1. Remove the steward's watching label named in that result, using `issue_write` with the PR's labels minus that one.
2. Subscribe again.
3. If events still don't arrive, rely on the hourly check-in for that PR. Note this on the dashboard.

**One actor per PR:** while you hold the lock, only your owners act on `task/` PRs. The `steward` skill defers to a live orchestrator.

### §5.5 Human messages in this session

Answer them.

- **Pause:** stop spawning, let running owners report, and keep check-ins going.
- **Stop:** as pause; then release the lock, delete your trigger, and unsubscribe from all PRs.

## §6 Merging

**Only the orchestrator merges.** Owners stop at `pr-ready`.

- **`human`** (default): never merge. Notify instead.
- **`auto`:** squash-merge a task PR only when **all** of these hold, re-checked immediately before merging:
  - CI is green on the head commit;
  - it's mergeable, with no conflict;
  - there are no unresolved review threads;
  - required checks pass, including the Claude Approvals check if the repo runs it;
  - a fresh `code-reviewer` on the final diff says `ship`.

  **Never** auto-merge:
  - device-notes PRs, or PRs for owner-task issues;
  - PRs touching `.github/workflows/release.yml` before T100 is done;
  - anything that isn't a `task/` PR.

## §7 Completion

**Complete** means every task-format issue (T01–T112 plus intake issues) is closed.

1. Spawn one owner (`MODE: fresh`, `TASK: cleanup`) for a PR that deletes the `docs/research/spikes/*` folders whose "delete when" condition is met.
2. Close the remaining epics and #3.
3. Post a final summary on #3.
4. Release the lock, delete the trigger, and send a final push notification.

If only human-gated work remains, keep the check-ins running, and say so on the dashboard.

## §8 Safety (you and every agent)

- **Isolation:**
  - One worktree per task (`/home/user/wt/<txx>`), on its own branch.
  - Never touch another task's worktree, branch, issue or PR.
  - Never commit on `main`. Never force-push or rebase a branch that has a PR.
- **Shared-machine locks:**
  - Git admin (`fetch`, `worktree add/remove`) runs under `flock -w 300 /tmp/talking-bear-git.lock -c '…'`.
  - Heavy commands (browser, `vite preview`, Playwright, `vitest --project browser`, Docker) run under `flock -w 540 /tmp/talking-bear-heavy.lock -c '…'`, with the Bash `timeout` set to 600000. Longer jobs use `run_in_background`.
  - Ports 4173–4175 and 8080–8082 are shared.
- **Sandbox limits:**
  - Don't run `playwright install`; browsers are in `/opt/pw-browsers`.
  - If a validation can't run in the sandbox (Docker, Go, espeak-ng, a browser version), use `ci-wait` with a draft PR, and cite the CI run.
  - Never edit configs, thresholds or tests to make something pass.
- **Rules from the issues:**
  - Never add unnamed dependencies.
  - Never store captured or real-voice audio.
  - Ask on ambiguity; never guess.
